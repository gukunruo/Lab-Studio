## 核心概念

### 1. Embedding 是什么

一段文本经 embedding 模型映射成一个**浮点数组**（如 768/1536 维）。语义相近的文本，向量夹角更小——常用 **cosine similarity**（余弦相似度）衡量远近。

**前端类比**：像把每段文本投影到一张多维地图上，语义近的点离得近。检索就是"找离问题最近的几篇"。

```python
# 一句话 embed
resp = httpx.post(f"{BASE_URL}/embeddings",
    headers={"Authorization": f"Bearer {API_KEY}"},
    json={"model": "text-embedding-3-small", "input": "前端性能优化"},
    timeout=60)
vec = resp.json()["data"][0]["embedding"]   # list[float]，1536 维
```

**不是干什么的**：

- 不是知识库本身（向量库存的是向量 + 元数据 + 原文引用，不是"知识"）
- 不能替代权限系统（检索到不代表用户有权看）
- 对"精确工号/订单号"类查询，往往不如关键词 / SQL（语义模糊，精确反差）

### 2. 相似度检索最小流程

```
离线（建索引）：文档 → 解析 → 切片 → 每片 embedding → 存向量库
在线（查询）：  问题 → embedding → 找 Top-K 近邻 → 取回原文片段 → 喂给 LLM
```

**两阶段**：建索引可慢（离线、Cron/CI），查询要快（延迟敏感，少做事）。索引要带版本（`builtAt` / git commit），不然换 embedding 模型后新旧向量不兼容。

### 3. 向量库是什么

存"向量 + 元数据（路径/标题/章节）+ 原文片段"的存储，支持"给一个向量找最近 K 个"。

| 方案 | 何时用 |
|---|---|
| 内存数组 + 纯 cosine | 起步、< 1 万片、Day 12 的迷你 RAG |
| 专用库（Chroma / Qdrant / pgvector） | 上规模、要持久化、要元数据过滤 |
| 托管（厂商向量服务） | 不想运维 |

**索引原理（知道即可）**：暴力 cosine 是 O(n)；专用库用 **HNSW（Hierarchical Navigable Small World，分层可导航小世界图）**等近似最近邻索引，牺牲一点精度换亚线性速度。**为什么知道这个**：选库时你要懂"近似"意味着召回不全，召回率是可调参数。

### 4. 切片（Chunking）直觉

文档要切成片才能 embed。切得好坏直接决定能不能检索到。

- **太大**：检索粗糙，一片含多个主题，塞进上下文浪费
- **太小**：丢失语境，检索到碎片拼不出完整答案
- **常用**：按标题/段落切，带重叠（overlap，如前后片各重叠 50 token），保留元数据（文件路径、标题、章节）
- **元数据是命脉**：没元数据就没引用、没权限过滤、没去重

**产品里怎么炸**：答案明明在文档里但检索不到——多半是切坏了（答案跨在两片边界）或切片粒度与问题粒度不匹配。overlap 能缓解边界问题。

### 5. RAG 标准架构（文字图）

```
┌─ 离线建索引 ──────────────────────────────┐
│  文档源 → 解析 → 切片 → Embedding → 向量库  │
└───────────────────────────────────────────┘
                    ↑ 查询时 embedding 比远近
┌─ 在线查询 ───────────────────────────────────────────────┐
│  用户问题 →(可选改写)→ Embedding → 检索 Top-K → 组装 Prompt → LLM → 回答(+引用) │
└─────────────────────────────────────────────────────────┘
```

关键：**质量取决于检索，而不只是模型**。模型再强，喂错片段就答错。

### 6. RAG 解决 / 不解决

| 解决 | 不解决 |
|---|---|
| 私有知识问答 | 复杂多步业务编排（要 Agent/工作流，Day 15） |
| 知识常更新（重建索引即可） | 数学证明、强推理本身变强 |
| 需要引用出处 | 检索错了时的"一本正经瞎编"仍可能发生 |

### 7. 失败模式速查

| 症状 | 多半是 |
|---|---|
| 答案在文档里但答不出 | 切坏了 / Top-K 太小 / 问题与文档用语不一致 |
| 答非所问 | Top-K 太大，噪声片段淹没了对的片段 |
| 一本正经瞎编 | 检索到的噪声全文塞给模型 + 没约束"不知则说不知" |
| 同义问题检索不到 | 缺 query 改写 / 混合检索（向量 + 关键词） |
| 索引换模型后全乱 | 新旧 embedding 不兼容，没带版本重建 |

### 8. RAG vs 微调 vs 长上下文

呼应 Day 03 的"长上下文 ≠ 全记得"：

- **长上下文**：小库可以直接全塞；大库仍要检索（成本 + lost-in-middle）
- **微调**：改行为/风格/领域格式；贵且慢；不替代文档更新
- **RAG**：工程上最常见、最便宜的"让模型懂你资料"
